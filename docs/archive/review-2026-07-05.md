## 保留した1件（→ 2026-07-06 修正済み）

> **2026-07-06 追記**: オーナー承認のもと masked live 再検証を試みたが、Chrome MCP の `javascript_tool` がページの `fetch`/`performance` と分離した world で動くため GraphQL 応答構造を観測できず未達。そこで**実 X 末尾形状に依存しない安全側の修正**（完了判定を `SyncCapture.isListTailResponse` に厳格化＝「Bottom cursor 有り かつ 非cursor entry が0」のページだけを末尾とする）を採用。誤完了を減らす方向にのみ作用し、データ誤消去は起こさない。`verify-sync-extraction`（単体）と `verify-sync-hook`（0ユーザー+item+Bottom cursor ページが完了を出さない回帰）にテスト追加、旧本体で FAIL することを TDD 確認済み。以下は当初の保留判断の記録。

**sync 完了判定 / reconcile の堅牢性**（medium, CONFIRMED）。`hasBottomCursor` が「0ユーザー＋Bottomカーソル」を一律で末尾とみなすため、途中ページ（凍結アカウント連続ページ等）で `sync-complete` が誤発火し、reconcile が同期済みリストを部分stagingまで削る恐れがある。結果は「まだブロック中のアカウントが一時的にフィルタから外れる（＝静かなフィルタ漏れ）」。真の末尾までスクロールするか、削除→再同期で復旧する。

**自走修正しなかった理由**: 完了判定はライブ検証済み（実アカウントで blocked 234 / muted 50 の同期成功）の契約で、正しい修正（「Bottomカーソル有り かつ 非カーソルの timeline entry がゼロのページだけを末尾とみなす」等）は実 X の末尾ページ形状に依存する。これは未確認であり、盲目的に変えると un-block を反映する reconcile を退行させ得る。**masked live 再検証（Chrome MCP・オーナー同意・構造のみ観測、raw 値なし）で X の末尾ページ形状を確認してから、synthetic fixture の回帰テスト付きで対応する**のが安全。新権限・raw 応答取得は不要。

## Completeness gaps（要観察・低優先・現時点で対応不要）

1. **引用カードの user_id 照合不可**: `processQuotedCards` は handle のみで判定（引用 DOM は handle しか出さない既知の制約）。実運用の同期エントリは handle を持つため影響は限定的。
